# AI Help Desk Triage Agent

An AI agent that reads an IT help desk ticket the way an employee wrote it, works out what the problem is and how urgent it is, finds the right knowledge base article, and drafts a reply for a human agent to review. It runs entirely on free, local models.

**[See it in action](https://jorgeabdulwork-coder.github.io/ai-help-desk-triage-agent/)** (no install needed) · **[Read the write-up](WRITEUP.md)** · **[Run the live demo](#live-demo)**

**Results at a glance**
- **97% fully correct** (problem type and priority) on 200 tickets no version had seen during tuning, up from 59% for the first prompt
- **Every priority decision is traceable:** the AI quotes evidence from the ticket, and code verifies the quote before raising priority
- **The review flag caught all 3** of the small model's classification mistakes in a 60-ticket run, by cross-checking the classifier against an independent knowledge base search
- **32% faster per ticket** by using a small model to classify and a larger one to write replies, with the same reply quality

Built to reflect real ITSM work at a multi-site retail organization (stores, donation centers, offices), where most ticket volume is repetitive and a good first pass saves agents time.

## Why synthetic data

All tickets in this repo are generated by `data/generate_tickets.py`. No real organizational or employee data is used. The generator mirrors realistic patterns (request mix, business-hours timing, POS issues limited to stores) and deliberately adds noise that makes triage hard: vague subject lines, typos, all-lowercase messages, tickets containing two unrelated issues, and business-impact phrases that should raise priority.

Each noisy ticket is tagged, so evaluation can report accuracy separately on clean and difficult tickets.

## Setup (free, runs locally)

The agent runs on a local open-source model through [Ollama](https://ollama.com), so there are no API costs.

1. **Install Ollama** from https://ollama.com/download (Windows and macOS installers). On Linux: `curl -fsSL https://ollama.com/install.sh | sh`
2. **Download a model:**
   ```bash
   ollama pull qwen2.5:7b
   ```
   About a 4.7 GB download; runs comfortably with 16 GB of RAM. On a machine with 8 GB, use `ollama pull llama3.2:3b` instead and set `LLM_MODEL=llama3.2:3b` in `.env`.
3. **Check it works:**
   ```bash
   ollama run qwen2.5:7b "Say hello in one sentence"
   ```
   On Windows and macOS the Ollama app keeps the server running in the background. On Linux, run `ollama serve` if it isn't already running.
   For Phase 4, also download the embedding model used for KB search (about 270 MB):
   ```bash
   ollama pull nomic-embed-text
   ```
4. **Set up Python** (3.9 or newer):
   ```bash
   python -m venv .venv
   .venv\Scripts\activate        # Windows
   source .venv/bin/activate      # macOS / Linux
   pip install -r requirements.txt
   ```
5. **Create your settings file:** copy `.env.example` to `.env`. The defaults already point at Ollama.

## Usage

```bash
python data/generate_tickets.py        # create the dataset (Phase 1)
python -m unittest discover tests      # check the logic, no model needed
python classify.py --dry-run           # see the exact prompt the model receives
python classify.py --limit 10          # classify 10 random practice tickets
python classify.py --explain INC-10204 # show every step of the decision for one ticket
```

Each run prints expected vs. predicted labels, the model's reasoning when it's wrong, and a summary, and saves full results to `results/predictions.csv`.

## Evaluation

`classify.py` is for quick checks on practice tickets. `evaluate.py` is the official score: it runs every ticket in the held-out set, which the prompt was never tuned on.

```bash
python evaluate.py --label baseline            # all 200 eval tickets (about 20 minutes locally)
python evaluate.py --label baseline --resume   # continue if the run was interrupted
python evaluate.py --rescore reports/baseline_predictions.csv   # rebuild a report without calling the model
```

Each run saves to `reports/`:

- `<label>_report.md`: accuracy for subcategory and priority, priority set too high vs. too low, accuracy on clean tickets vs. each kind of noise, a priority comparison table, the most common category mix-ups, and example misses with the model's reasoning
- `<label>_predictions.csv`: every ticket with correct and predicted labels
- `runs.csv`: one line per run with the model, prompt version, and scores, to compare improvements over time

The prompt has a version number (`PROMPT_VERSION` in `triage/classifier.py`). Change it whenever you edit the prompt so each run in `runs.csv` shows which version it measured.

### Data files

| File | Contents |
|---|---|
| `tickets_train.csv` | 2,800 tickets for development and prompt tuning |
| `tickets_eval.csv` | 200 held-out tickets, only used to score the agent |
| `kb_articles.json` | 18 KB articles, one per subcategory |

`ticket_id`, `created_at`, `requester`, `role`, `location`, `subject`, `description` are what the agent sees. `category`, `subcategory`, `priority`, `kb_article` are the correct labels. `tags` lists the noise applied (`escalated`, `vague_subject`, `multi_issue`, `typos`, `lowercase`). Priority is Low, Medium, High, or Urgent; an `escalated` ticket describes wider business impact and is one level above its subcategory's normal priority.

## How the classifier works

The work is split: **the AI reads the ticket, the code applies the business rules.**

1. **Prompt:** instructions with the valid subcategories, rules for telling similar ones apart, the raise rules for priority, and nine hand-written examples whose reasons point to specific evidence in each ticket.
2. **Structured output:** the AI answers with JSON matching a schema: a one-sentence reason, the category and subcategory, which raise rule applies (`none`, `several_people`, `customers_waiting`, or `cannot_work`), and the exact words from the ticket that prove it. There is no priority field.
3. **Validation and self-correction:** every answer is checked against the real category list. An invalid answer is sent back with the specific error for one more try.
4. **Priority in code:** the subcategory's default priority comes from the KB file (like an SLA matrix). It goes up one level only if a raise rule was claimed and the quoted evidence passes two checks: it really appears in the ticket (allowing for small typos), and it actually says what the rule requires, such as mentioning several people or customers for those rules. Anything else keeps the default.

To see every step for one ticket: `python classify.py --explain INC-10204`

The client uses the OpenAI-compatible API, so switching to GitHub Models or Azure AI Foundry only means changing `.env`.

## The full agent (Phase 4)

```bash
python run_agent.py INC-10204
python run_agent.py --subject "Scanner broken" --description "Scan to email stopped working on the copier."
python evaluate_agent.py --label agent-qwen      # 30 evaluation tickets
```

For each ticket the agent:

1. **Classifies it** with the classifier above.
2. **Suggests KB articles.** The article for the predicted subcategory is used for the reply. Separately, the ticket text is compared by meaning against every KB article using embeddings (vectors of numbers that represent meaning, compared with cosine similarity), and the closest matches are listed as related articles. Article vectors are cached, so they are only recomputed when an article changes.
3. **Flags tickets for review** when the classifier and the KB search disagree about which article fits, giving a human a second look where the two signals conflict.
4. **Drafts a reply** in a second AI call that may only use the steps in the chosen KB article. Steps are split into what the employee can try and what IT will do, so the reply never asks the employee to do IT's work.
5. **Checks the reply** with fast rules: greets the requester by name, stays short, never asks for a password, contains no links or phone numbers the KB doesn't have, and signs off correctly. Any failure flags the ticket for review.

Every reply is a draft for a human agent to review and send.

**Evaluation** (`evaluate_agent.py`) measures KB suggestion accuracy, how well the search does on its own, whether the review flag catches classifier mistakes, the safety check pass rate, and grades from an **AI judge** that checks each reply is grounded in the KB article, addresses the problem, and has a suitable tone. The judge is itself an AI and can be lenient, especially when grading its own model's writing, so the report includes sample replies for a human to verify.

### Agent results

| Run | Classifier model | Replies passing safety checks | Grounded (judge) | Steps fit (judge) | Classifier mistakes caught by review flag |
|---|---|---|---|---|---|
| Reply rules r1, judge j1 | qwen2.5:7b | 100% | 80%, but most flags were false alarms (see below) | not measured | 0 of 0 (no mistakes in the sample) |
| Reply rules r2, judge j2 | llama3.2:3b (judge: qwen2.5:7b), 60 tickets | 100%, but checks missed real problems (see below) | 26.7% as graded, 53.3% after removing 16 likely false alarms | 50% | **3 of 3**, with 3 false alarms |
| Reply rules r3, judge j3 | qwen2.5:7b, 30 tickets | 100% | 63.3% as graded, **96.7%** after removing 10 likely false alarms | 80% | 0 of 0 (no mistakes in the sample) |
| Reply rules r3, judge j3 | llama3.2:3b classifies, qwen2.5:7b writes, 60 tickets | 100% | 50.0% as graded, **90.0%** after removing 24 likely false alarms | 70% | **3 of 3**, with 3 false alarms |

**What the first run showed:** KB suggestions and the safety checks were perfect on 30 tickets, but reading the replies as a help desk professional revealed problems the metrics missed:

- **The judge was wrong more often than the replies.** A manual review of its 6 "not grounded" flags found most were false alarms: it flagged steps that were in the KB article, and a sentence the reply rules require for urgent tickets, because it hadn't been given those rules.
- **Grounded is not the same as helpful.** A scan-to-email ticket got printing steps, because the KB article only covered printing. The reply followed the article faithfully and still didn't help. Expired-password tickets got "check Caps Lock" for the same reason. **The AI's answers are only as good as the knowledge base behind them.**
- **Internal wording leaked into replies,** such as "For IT, we will..." copied from the prompt's own labels.

**Changes:**
- **KB content:** scan-to-email steps added to the printer and scanner article, and the password article now separates forgotten and expired passwords.
- **Reply rules r2:** use only the steps that fit the specific problem, describe IT's actions naturally ("we'll re-add the printer for you"), mention separate tickets only for a real second problem, and put the sign-off on its own line. New safety checks catch internal labels and a misplaced sign-off.
- **Judge j2:** the judge sees the reply rules, grades whether the chosen steps fit the problem, and must quote any sentence it considers invented. The code then checks that quote against the KB article and marks likely false alarms, the same pattern used to verify the classifier's escalation evidence.

**What the r2 Llama run showed:** the **review flag worked**: it caught all 3 classifier mistakes in 60 tickets, with 3 false alarms. In a live demo, Llama classified a scan-to-email ticket as Peripherals, the KB search matched Printer/Scanner instead, and the ticket was flagged before a wrong reply could be sent. But Llama could not write good replies. It pasted the one example sentence from the reply rules ("we'll re-add the printer for you") into Outlook, Wi-Fi, and VPN replies, guessed at causes the KB never mentioned, mentioned KB numbers and priority levels, and rewrote employee steps as things IT would do. The rule-based checks passed all of these because none were designed for these patterns; the judge caught most of them, and its quote check correctly identified 16 of its 44 flags as likely false alarms. **The conclusion: a small model can classify well with code guardrails, but writing needs a larger model.**

**Changes in r3 and j3:**
- Reply rules describe the format without any example sentence a model could copy, forbid guessing causes and mentioning KB numbers, categories, or priority levels, and require employee steps to be written as things for the employee to try.
- The KB article number is no longer shown to the reply writer, and the classification is marked as internal notes.
- New checks catch KB numbers, priority levels, guessed causes ("due to", "caused by"), and any device or system the reply mentions that appears in neither the ticket nor the KB article. Every pattern from the r2 Llama report is a unit test.
- Extra blank lines are cleaned up automatically.
- `LLM_REPLY_MODEL` lets a different model write replies, so a small fast model can classify while a larger one writes.
- The judge's note must be a plain sentence (j2 sometimes returned a field name).

**What r3 showed:** reply quality improved sharply. No copied sentences, no internal labels, KB numbers, priority names, or guessed causes, and a consistent format. Two further findings:

- **The judge needs checking more than the replies do.** In the Qwen run, 10 of the judge's 11 "not grounded" flags quoted text that was actually in the KB article, and the remaining one quoted the reply's own acknowledgment sentence. Without the code's quote check, the judge would have reported 63% grounded instead of roughly 97%. Its "steps fit" grades are also mixed: it is right that "check Caps Lock" doesn't help an expired password, but debatable on others, such as suggesting a different port before replacing a broken mouse. A next step would be to label a small set of replies by hand and measure how often the judge agrees.
- **Splitting models works.** With Llama classifying and Qwen writing, average time dropped from 28.2 to 19.2 seconds per ticket (about 32% faster), reply quality matched the Qwen-only run, and the review flag caught all 3 of Llama's classification mistakes. The trade-off is slightly lower classification accuracy, covered by the flag and human review.

**Remaining known issues:**
- **KB content still limits replies.** Expired-password tickets still get "check that Caps Lock is off," and "VPN connects but no shared drive access" isn't covered by the VPN article at all. Labeling steps by situation worked well for the printer article ("Printing:", "Scan to email:"), where print tickets correctly got only printing steps, so the same structure would likely fix the password article. Structured KB content proved more reliable than prompt instructions.
- **Employee steps are occasionally rewritten as IT actions** ("We will wait 15 minutes before trying again").
- **The quote check doesn't know phrases the rules require,** so the judge flagging "we are already working on it" on an urgent ticket was marked as confirmed rather than as a false alarm.

**Honest note on the KB:** this dataset has one article per subcategory, so the suggested article is correct whenever the classification is. The search matters more in a real KB with hundreds of overlapping articles; here it mainly serves as the independent second opinion behind the review flag.

## Results

Scores on the 200 held-out tickets.

| Prompt | Model | Subcategory | Priority | Fully correct | Priority too high / too low |
|---|---|---|---|---|---|
| v1 | llama3.2:3b | 90.5% | 64.5% | 59.0% | 58 / 13 |
| v2 | llama3.2:3b | 95.0% | 85.0% | 83.0% | 24 / 6 |
| v3 | llama3.2:3b | 94.5% | 70.5% | 69.5% | 58 / 1 |
| v3 | qwen2.5:7b | 95.5% | 89.0% | 89.0% | 22 / 0 |
| v4 | llama3.2:3b | 95.5% | 96.0% | 94.5% | 5 / 3 |
| v4 | qwen2.5:7b | 98.5% | 98.5% | 98.0% | 2 / 1 |

**What the v1 baseline showed:** classification was strong, but the model over-prioritized, raising priority for reasons outside the rules, such as how long an issue had lasted or the ticket coming from a store. The word "shared" pulled Outlook and folder-access tickets into Shared Mailbox, and the small model copied one example's reasoning word for word into unrelated tickets. **v2 changes:** a default priority for each subcategory with an explicit list of what does and doesn't raise it, rules for commonly confused subcategories, and rewritten examples with ticket-specific reasoning. The fixes were written as general rules rather than to match individual evaluation tickets.

**What v2 showed:** fully correct rose from 59% to 83%. The remaining priority errors came from the AI inventing impact the ticket never stated ("the whole store being affected" for one frozen register) and from answers where the reason was right but the priority didn't match it. **v3 changes:** the AI no longer outputs a priority. It reports which raise rule applies and quotes the evidence, and the code calculates the priority, rejecting any raise whose evidence isn't in the ticket. A simulation with perfect AI answers reproduces all 200 correct priorities, confirming the rules in code are complete. v3 also added distinction rules for Desk Phone, Peripherals, and VPN, which the v2 report showed being confused; since these came from reviewing evaluation misses, they may slightly flatter the v3 score on those subcategories.

**What v3 showed:** with Qwen, v3 was the best result so far, with zero tickets under-prioritized. But it made the smaller Llama model worse. The evidence check confirmed the quote existed in the ticket, not that it proved the rule, and Llama learned to claim "several people affected" while quoting any real sentence, such as "My account got locked about an hour ago." The same prompt design worked for the larger model and backfired on the smaller one. Qwen's main remaining error was classifying Teams sign-in problems as Outlook, because the prompt had a distinction rule for Outlook but none for Teams. **v4 changes:** a second check that the quote actually fits the rule (for example, a "several people" quote must mention several people), and a Teams distinction rule. Every bad quote from the v3 reports is now a unit test.

### Final score on unseen tickets

The prompt was improved three times using feedback from the evaluation set, which makes that set's score gradually optimistic. The final score comes from a fresh set generated with a new seed after tuning was finished:

```bash
python data/generate_tickets.py --test-set fresh --seed 2026 --count 200
python evaluate.py --label final-qwen --input data/tickets_fresh.csv
```

| Test set | Model | Subcategory | Priority | Fully correct | Priority too high / too low |
|---|---|---|---|---|---|
| Fresh, unseen | qwen2.5:7b | 99.5% | 97.0% | **97.0%** | 1 / 5 |

**What v4 showed:** the second evidence check fixed the small model's regression, taking Llama from 69.5% to 94.5% fully correct. The code rejected 66 of Llama's escalation claims, so the guardrails did much of the work a larger model would otherwise do. Llama averaged about 7 seconds per ticket against 12 to 18 for Qwen, a real speed and cost trade-off. On the fresh set, Qwen scored 97.0%, close to its 98.0% on the tuned evaluation set, which suggests the tuning generalized rather than memorizing specific tickets.

**Remaining failure modes on the fresh set:** all 5 under-prioritized tickets were escalations the AI understood correctly but that the evidence checks rejected. In some, the AI paraphrased instead of quoting ("customers are waiting" for a ticket that said "a line of customers waiting"). In others, it chose the wrong rule name for a correct quote ("affecting all the registers" labeled as several people instead of customers waiting). The checks that stopped invented escalations in v2 and v3 now occasionally block real ones, which trades over-prioritization for under-prioritization, the more costly direction in a help desk. Likely fixes are accepting a quote that fits any raise rule (since every rule raises by the same one level) and a looser match for paraphrased quotes. These were not applied, so the fresh-set score stays an honest measurement; any fix would need another unseen test set to measure it.

## Known limitations

- The phrase lists that confirm evidence fits a raise rule were written with this dataset's wording in view. Real tickets describe impact in many more ways ("half the team," "the whole back room"), so production use would need a broader list or a second AI check that judges whether the quote supports the rule.

- Template-based text is more uniform than real tickets, so accuracy here will overstate real-world performance. A planned improvement is an LLM paraphrasing pass to diversify wording while keeping labels fixed.
